# c7-candidature-fictive-01 — Candidature complète jusqu'au clic final, sur page fictive

Chantier C7 (étapes 1-5) du `.manager/PLAN-04-11.md`. Dossier `~/Downloads/agregat-back-astra`, branche `suite-astra`, base **159567a** (arbre propre). Modèle : Opus. Un seul sous-agent dans l'arbre ; le manager n'y écrit que des rapports pendant ce chantier.

## But
Prouver, sur une page fictive servie en local, que Relay mène une candidature multi-étapes jusqu'au bouton « Envoyer » et s'y arrête en `waiting_permission` avec un aperçu, sans jamais envoyer sans clic : refus → 0 envoi, accord → exactement 1 envoi, annulation → 0 envoi, plafond configuré → expiration tracée. L'étape 6 (offre réelle, clic du propriétaire) n'est pas dans ce brief.

### Point 2 — Page fictive de candidature à 3 étapes et parcours de bout en bout
Nouveau `tests/support/apply-page.js` : serveur `http` local (port 0 ou ≥ 4320, jamais 4310/5173/19988), tout marqué **FICTIF** :

Nouveau `tests/apply-flow.test.js` (Chrome réel, `skip` si Chrome absent, comme `browser-click-ref.test.js`) avec `BrowserGateway` + `CdpBrowser` + `RunPolicy({ ownerMode: true, allowLocalOrigins })` et un `approve` contrôlé par le test : navigate → fillForm (étape 1) → clic « Suivant » (**aucun** appel à `approve`) → upload d'un `cv-FICTIF.pdf` écrit dans le dossier du run → clic « Suivant » (aucun accord) → fillForm (étape 3) → snapshot de relecture → clic « Envoyer » → `approve` appelé **une fois** avec `actionClass: 'send'` et un `preview` non vide (sans texte de page complet). Quatre issues, chacune un cas de test : refus → erreur « Action refusée » et `/count` = 0 ; accord → `/count` = 1 et page « reçue » ; annulation (promesse résolue `cancelled`) → `/count` = 0 ; plafond (`AGENT_PLATFORM_SEND_TIMEOUT_MS` ou `permissionTimeoutMs` réduit, selon ce que le test peut injecter) → `expired` tracé, `/count` = 0. Le test est le seul à « cliquer » : aucun accord `send` accordé par du code de production.

### Point 3 — Capacités `browser.dialog` et `browser.verify` (deux commits)
- `browser.dialog { accept: boolean, promptText?: string }` : `cdp.js` pose `page.on('dialog')` à l'ouverture de la page ; le dialogue en attente est mémorisé (type, message tronqué à 200 caractères) et exposé dans le résultat de l'appel qui l'a déclenché (`dialog: {type, message}`) ; `browser.dialog` l'accepte ou le refuse ; sans dialogue en attente : erreur claire. `beforeunload` : le dialogue est accepté ou refusé par cette capacité, jamais en silence ; test sur la page fictive (navigation après modification d'un champ).
- `browser.verify { ref?, text?, value? }` : relit, sans rien modifier, la valeur d'un champ ou la présence d'un texte ; renvoie `{ ok, actual }` (valeur tronquée à 200 caractères, jamais pour un champ sensible : `textLength` seulement, même règle que `browser.type`). Déclaration dans `capability-registry/index.js` (`effect: 'read'`), `mcp-contract.test.js` mis à jour, schéma strict.
Les deux capacités s'ajoutent au `FixturePageProvider` (`browser-gateway/index.js:221`) si les tests existants en dépendent ; sinon le dire.
