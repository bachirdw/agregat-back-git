### Chemin réel de l'erreur (constaté dans le code)

1. `RunPolicy.resolveUrl()` (`run-policy.js`) lève « Résolution DNS impossible : <hôte> » (ou URL invalide,
   identifiants, protocole, port, IP directe, domaine non autorisé, réseau privé).
2. `BrowserGateway.execute()` (`browser-gateway/index.js`, ligne `if (args.url) await this.policy.assertUrl(args.url)`)
   l'appelle en tout premier, avant `provider.prepare`, avant toute lecture de la page et toute action.
3. Le serveur MCP (`mcp-gateway/server.js`, processus enfant en stdio) attrape l'erreur dans `failure(e)` et renvoie
   `{ isError: true, content: [{ type: 'text', text }] }` : seul le texte franchit la frontière du processus.
4. `workflow-run.js` (exécuteur `tool`) lève `Outil <nom> : <texte>` : une `Error` nue.
5. `launch()` (`workflow-engine/index.js`) : étape non rejouable → `uncertain` ; l'expiration ne visait que `agent`.

Piège : `policy.assertUrl` est aussi appelé PENDANT une action (`cdp.js` : redirections suivies, routes, sauts d'un
téléchargement après une première requête ; `FixturePageProvider` : redirection). Marquer « sans effet » toutes les
erreurs de la politique serait faux : la marque doit dépendre de la position de l'appel.

### Choix du transport (le plus petit)

- On réutilise la marque structurée existante `actionDone: false` (E66, `policy-engine/not-done.js`) plutôt qu'un
  nouveau concept : même sens (« levée avant d'agir »), déjà lue par la passerelle MCP et l'API.
- `run-policy.js` : `assertUrl(raw, { beforeAction })`. La politique pose la marque sur sa propre erreur, mais
  seulement quand l'appelant déclare n'avoir encore rien fait. Sans option : inchangé (redirections, sauts de
  téléchargement de `cdp.js` restent non marqués).
- `browser-gateway/index.js` (1 ligne) : le premier contrôle de `execute()` (`args.url`), avant `provider.prepare`,
  passe `{ beforeAction: true }`. C'est le seul endroit où l'on est certain qu'aucun effet n'a eu lieu.
- `mcp-gateway/server.js` (`failure()`, 2 lignes) : la marque ne franchissait pas le processus stdio ; elle est
  ajoutée en `_meta: { actionDone: false }` du résultat, **seulement** pour les appels de l'exécuteur de workflow
  (`RELAY_TOOL_CALL_PREMETERED === '1'`). Les réponses lues par un agent restent identiques à l'octet.
- `workflow-run.js` : l'erreur « Outil <nom> : <texte> » reprend `actionDone: false` si `_meta` le porte.
- `workflow-engine/index.js` : `launch()` met `failed` (avec `finished_at`) une étape non rejouable non `agent` dont
  l'erreur porte `actionDone === false` ; sinon `uncertain` comme avant. L'expiration de `uncertain` vaut pour
  tous les genres ; message agent inchangé, autres genres : « Étape à l’effet incertain, sans décision humaine
  après N s (réglable : AGENT_PLATFORM_HUMAN_WAIT_MS) : <cause> » / « … (mode non supervisé) : <cause> ».
- Doc : paragraphe « États d'une étape de workflow » ajouté dans `docs/architecture.md` (aucun document ne
  décrivait ces états ; l'ADR 003 renvoyait leur nom au sprint 03).

## Pourquoi la démonstration fictive est partie avec le vrai navigateur (lecture du code, rien codé)

- `Orchestrator.plan()` (`orchestrator/index.js`, vers la ligne 795) : `browser: 'auto'` devient `playwriter` en
  mode propriétaire (sinon `isolated` en live, `fixture` seulement hors live). `mcpServerFor()` prend
  `run.browser`, sinon la même règle. Le champ `browser` de la mission ne dépend donc que du mode, pas du pack.
- `dataMode: fixture` du pack `najah` n'est lu que pour le Bilan et career-ops (`plan.dataMode`, lignes ~1174, 1977,
  2019) : il ne force pas `RELAY_BROWSER=fixture`.
- `https://jobs.example.test` est l'adresse par défaut du `FixtureBrowser` (`browser-gateway/index.js`, ligne 19) et
  l'argument de l'étape `snapshot` du DAG Najah. Avec le vrai navigateur, la politique propriétaire (domaines vides
  = tout domaine admis) résout ce nom réservé `.test` : DNS impossible → E160.
